# Codex Agent Switch 持久化设计文档

> 文档类型：Persistence Design Specification  
> 项目暂定名称：Codex Agent Switch  
> 简称：CAS  
> 当前目标版本：V0.1  
> 文档职责：定义 CAS 本地业务数据的持久化方案、数据库结构、约束、索引、事务边界、Repository 映射、Schema Migration、数据生命周期与恢复原则。

---

# 0. V0.1 持久化基线

V0.1 Schema 只承载 Provider、CredentialReference、Model、Agent、Base Binding、Configuration Projection、Snapshot / Recovery 与 Setting。Profile、ProfileAgentBinding、Discovery Cache、Runtime Probe / Verification History 和复杂 Capability Evidence History 为 P1，不进入初始 Migration。

DeepSeek V4 Flash 与 Custom Responses Provider 共享同一表结构；禁止使用品牌专表。凭据值只在 Windows Credential Manager，SQLite 仅保存引用。Ownership 使用语义指纹，`content_hash` 只用于诊断。

---

# 1. 文档目标

CAS 需要长期保存以下本地业务状态：

```text
Provider
Model
Agent
Agent ↔ Model Binding
Profile
Profile ↔ Agent ↔ Model Binding
Credential Reference
Managed Resource
Configuration Snapshot Metadata
Application Settings
Apply Transaction Metadata
Compatibility / Verification Metadata
```

这些数据需要满足：

```text
本地优先
可靠
可迁移
可恢复
结构清晰
支持事务
支持约束
跨平台
无需独立数据库服务
```

因此 V0.1 默认采用：

> SQLite 作为 CAS 核心本地持久化数据库。

---

# 2. 持久化边界

CAS 持久化系统只保存：

```text
CAS 自己拥有的业务状态
```

不负责把 Codex 整个环境复制到数据库。

关系：

```text
CAS Domain State
        │
        ▼
      SQLite

Codex Configuration
        │
        ▼
Filesystem
```

二者必须分离。

---

# 3. SQLite 的职责

SQLite 保存：

```text
用户添加了哪些 Provider

Provider 下有哪些 Model

有哪些 Agent

Agent 当前绑定什么 Model

有哪些 Profile

哪个 Profile 当前激活

CAS 管理了哪些 Codex Resource

最近一次 Apply 状态

Configuration Snapshot 元数据

Provider / Model 验证信息

CAS 应用设置
```

SQLite 不保存：

```text
完整 config.toml

完整 agents/*.toml

Codex Session

Agent Conversation

LLM Response

Shell Output

项目代码

完整运行日志
```

---

# 4. Secret 不进入普通数据库

以下内容禁止进入 SQLite 明文字段：

```text
API Key
Bearer Token
Access Token
Refresh Token
Password
Private Key
敏感 Header Value
```

SQLite 中只保存：

```text
CredentialReference
```

例如：

```text
credential_id
provider_id
secret_type
storage_backend
storage_key
```

真正 Secret 由：

```text
Operating System Secret Store
```

保存。

```text

├── cas.db

├── backups/
│
├── journals/
│
├── logs/
└── cache/
```

# 10. SQLite 基础设置

数据库初始化时至少启用：

```sql

```


```text

```

```text

```

# 11. WAL 使用原则

推荐：

```text

```

原因：

```text
提高并发读能力
降低 GUI 查询与后台写事务冲突
```

但 CAS 不应因为 WAL 就假设：

```text
多进程无限并发写
```

业务写操作仍需要受 Application 层事务管理。

# 24. Provider 删除与 Credential

Provider 被正式删除时：

```text
CredentialReference
```

不得通过：

```text
ON DELETE CASCADE
```

绕过应用层直接从 SQLite 删除。

正确流程必须由 Secret Application Service 先协调 OS Secret，再删除 CredentialReference，最后删除 Provider；任一步失败都不得留下“数据库已删、Secret 遗留”的假成功状态。

真正 OS Secret 是否同时删除：

```text
不能依赖数据库级联。
```

必须由 Secret Application Service 协调，因此外键使用 `ON DELETE RESTRICT`。

---

# 25. 为什么 Credential 外键必须 Restrict

CredentialReference 虽依赖 Provider 存在，但它指向的：

```text
Operating System Secret
```

是数据库事务之外的外部资源。

如果数据库自动级联：

```text
Provider row deleted
CredentialReference row deleted
OS Secret cleanup failed / never executed
```

就会产生不可追踪的 Secret 遗留。

因此必须：

```text
Application Service 协调 Secret 删除
        ↓
删除 CredentialReference
        ↓
删除 Provider
```

数据库外键只负责用 `RESTRICT` 防止绕过流程。

# 46. Active Profile 唯一约束

SQLite 无法通过普通：

```text
UNIQUE(is_active)
```

实现，因为：

```text
false
```

会重复。

推荐 Partial Unique Index：

```sql
CREATE UNIQUE INDEX idx_profiles_single_active
ON profiles(is_active)
WHERE is_active = 1;
```

确保：

```text
最多一个 Active Profile。
```

# 53. ManagedResource 的作用

该表用于回答：

```text

这个 Provider Fragment 是不是 CAS 管理的？

上一次 Apply 时内容是什么？

它是否可能被外部修改？
```

它不是：

```text
Codex Config 内容存储表。
```

---

# 54. `physical_location`

保存：

```text
实际资源位置
```

例如：

```text
C:\Users\x\.codex\agents\cas-executor.toml
```

该字段可以随：

```text
CODEX_HOME
```

变化更新。

不能作为业务身份。

---

# 55. `logical_key`

例如：

```text
provider:cas_deepseek

agent:executor

catalog:deepseek
```

用于稳定定位逻辑资源。

---

# 56. Semantic Hash 与 Content Hash

对于完整 CAS-owned 文件，Ownership 判定使用：

```text
semantic_hash
```

保存：

```text
canonical semantic hash
```

推荐：

```text
SHA-256
```

`content_hash` 可保存完整字节 Hash，仅用于诊断展示，不参与 Ownership / Conflict 判定。

---

# 57. Fragment Hash

对于：

```text
config.toml
```

这样的 Shared Resource：

```text
fragment_hash
```

保存：

```text
CAS-owned logical fragment
```

的规范化 Hash。

---

# 58. `origin_entity`

例如：

```text
origin_entity_type = AGENT
origin_entity_id   = <executor UUID>
```

用于：

```text
ManagedResource
→
Domain Entity
```

追踪。

数据库不建立通用：

```text

```

因为：

```text
origin_entity_id
```

可能指向多种实体。

应用层负责校验。

# 76. Database Transaction 与 Apply Transaction

```text

```





# 107. 唯一约束优先数据库保证

以下规则不能只靠业务代码：

```text
Provider Key 唯一

Provider + Model ID 唯一

Agent Key 唯一

Profile Key 唯一

Profile 内 Agent 唯一

Active Profile 最多一个
```

应尽量使用：

```text
Database Constraint
```

作为最后一道防线。

---

# 108. Foreign Key 必须启用

SQLite 默认 Foreign Key 行为取决于连接设置。

每个数据库 Connection 必须确保：

```sql
PRAGMA foreign_keys = ON;
```

不能只在数据库初始化时执行一次然后假设所有 Connection 都有效。

---

# 109. Check Constraint

适合稳定小范围字段：

```sql
CHECK(enabled IN (0, 1))
```

但大型 Domain Enum 是否直接写 CHECK，要考虑未来迁移成本。

V0.1 可以让：

```text
Enum Validity
```

主要由 Domain 层控制。

---

# 110. Null 语义

必须保持：

```text
NULL = Unknown / Not Specified
```

与：

```text
0 / empty string
```

分离。

例如：

```text
context_window = NULL
```

表示不知道。

不要保存：

```text
context_window = 0
```

---

# 111. 空字符串

对必填文本：

```text
name
key
model_id
```

Domain 层禁止：

```text
""
```

数据库 `NOT NULL` 不能阻止空字符串。

必要时可以：

```sql
CHECK(length(trim(name)) > 0)
```

但 V0.1 可以由 Domain Validation 负责。

---

# 112. URL

Provider `base_url` 在数据库中保存：

```text
规范化后的字符串
```

但不要过度修改用户语义。

例如：

```text
是否保留 trailing slash
```

应由 Provider Domain / Adapter 有一致规则。

---

# 113. Metadata JSON

所有 JSON 写入前必须：

```text
Serialize
↓
Validate
```

读取失败不得：

```text

```

需要转换为 Persistence Error。

# 114. JSON Schema Version

对于未来可能演进的大型 JSON：

```text

details_json
```

如果其结构参与业务，建议内部包含：

```text

```

或者数据库单独记录版本。

# 115. Schema Migration

数据库必须从 V0.1 开始就使用正式 Migration。

禁止：

```text
启动时 CREATE TABLE IF NOT EXISTS
然后长期靠手工加字段。
```

```text
migrations/
├── 0001_initial.sql
├── 0002_xxx.sql
└── ...
```

已经发布的：

```text

```

不得为了修问题直接编辑。

必须新增：

```text

```

否则旧用户数据库无法稳定升级。

如果使用 SQLx：

可以使用其：

```text
_sqlx_migrations
```

机制。

如果自己实现，维护：

```text

```

但不要同时维护两套 Migration Source of Truth。


# 119. Migration 前备份

```text

```

或者跨重要版本升级时，建议：

```text

```

```text

```

降低升级风险。

# 120. Migration Transaction

只要 SQLite 允许，应在：

```text

```

中执行单次 Migration。

Migration 中途失败：

```text

```

---

# 121. Destructive Migration

例如：

```text

重建表
改变主键
```

必须采用：

```text

copy valid data
validate
swap
```

模式。

不要：

```text
先删旧数据再迁移。
```

---

# 122. Forward Migration Only

正式版本默认只支持：

```text
旧 Schema
→
新 Schema
```

不保证：

```text
新版本数据库
→
旧版本程序
```

可以安全使用。

# 123. Database Schema Version Too New

用户用旧版 CAS 打开新版数据库：

必须：

```text

```

返回：

```text
DATABASE_SCHEMA_TOO_NEW
```

避免旧程序破坏新字段。

# 124. First Run Initialization

首次运行：

```text

```

```text

```

```text

```

# 125. Preset 不全部入库

默认从：

```text

```

加载。

只有用户：

```text

```

后才成为业务实体。

Preset 属于：

```text

```

而 Provider / Agent 属于：

```text

```

二者生命周期不同。



展示。

```text

```

或专门 ExternalState 表。

# 129. ExternalState 是否持久化

```text

```

每次：

```text

```

重新获取。

只将：

```text
ManagedResource
```

长期持久化。

---

# 130. 派生状态不重复保存

以下状态优先实时计算：

```text

ModelAvailability

AgentAvailability

ProfileStatus

EffectiveCapabilities

PendingChanges
```

不要每次变化都：

```text
UPDATE 一堆 status 字段。
```

---

# 131. 为什么不持久化派生状态

例如 Agent 是否 Ready 依赖：

```text

Binding

Model enabled

Provider enabled

Credential

Compatibility
```

如果再保存：

```text
agents.status
```

极易出现：

```text
Provider disabled
但 Agent.status 还是 READY。
```

---

# 132. 可缓存派生状态

如果未来计算很重，可以增加：

```text
Cache
```

但 Cache 必须：

```text
可删除
可重新生成
不作为 Source of Truth。
```

---

# 133. Pending Changes 不直接存 Boolean

不要：

```text
application_settings.pending_changes = true
```

作为唯一来源。

应根据：

```text
Desired State Fingerprint
+
Last Applied Fingerprint
+
Observed Drift
```

计算。

---

# 134. Applied State

推荐持久化：

```text
last_applied_desired_hash
```

或者独立：

```text
configuration_state
```

表。

例如：

```sql
CREATE TABLE configuration_state (
    id                        INTEGER PRIMARY KEY CHECK(id = 1),
    last_applied_desired_hash TEXT,
    last_applied_at           TEXT,
    last_apply_transaction_id TEXT
);
```

始终只有：

```text
一行。
```

---

# 135. Singleton 表

如果采用：

```text
configuration_state
```

使用：

```text
id = 1
```

作为 Singleton。

不要将这种全局结构塞入：

```text
application_settings
```

通用 key-value。

---

# 136. Configuration State 与 Managed Resource

```text
configuration_state
```

回答：

```text
整个 CAS Desired State
上次何时 Applied？
```

`managed_resources` 回答：

```text
某个具体 Codex Resource
上次是什么状态？
```

两者职责不同。

---

# 137. Apply 成功后的数据库事务

文件 Apply 成功并完成验证后：

使用一次数据库事务更新：

```text
ManagedResource fingerprints

Configuration State

Apply Transaction status = COMMITTED

Snapshot linkage
```

避免数据库内部出现：

```text
Agent 文件已经 Apply
但 ManagedResource 还是旧 hash
```

---

# 138. 数据库更新失败

如果：

```text
Codex 文件已经成功写入
```

但：

```text
SQLite Commit 失败
```

系统不能简单返回普通失败。

这属于：

```text
State Tracking Failure
```

应进入：

```text
RECOVERY_REQUIRED
```

下一次启动重新扫描：

```text
Observed Codex State
```

进行恢复。

---

# 139. Database Backup 与 Codex Snapshot 分离

必须区分：

```text
CAS Database Backup
```

和：

```text
Codex Configuration Snapshot
```

前者保护：

```text
CAS 自己的数据。
```

后者保护：

```text
Codex 外部配置文件。
```

不能混为一个 Backup。

---

# 140. Restore Codex 不回滚数据库

执行：

```text
Restore Codex Snapshot
```

默认只恢复：

```text
Codex Files
```

不会：

```text
恢复 cas.db。
```

因此恢复后可能出现：

```text
Desired CAS State
≠
Observed Codex State
```

这属于正常 Drift。

---

# 141. CAS Database Recovery

如果 CAS 自己数据库损坏，应使用：

```text
Database Backup
```

恢复。

不能拿：

```text
Codex Configuration Snapshot
```

还原业务数据库。

---

# 142. SQLite Corruption

启动时如果 SQLite 返回：

```text
corrupt
malformed
```

CAS 不应自动：

```text
删除数据库并重建。
```

应：

```text
进入 Recovery / Read-only Error State
```

并保留原文件。

---

# 143. 数据库完整性检查

可在：

```text
Diagnostics
```

或者升级后使用：

```sql
PRAGMA quick_check;
```

必要时：

```sql
PRAGMA integrity_check;
```

不要每次普通查询都运行完整 Integrity Check。

---

# 144. Application Crash

SQLite WAL 可以降低数据库损坏风险。

但 Application 仍应：

```text
避免超长事务

尽快 Commit

避免在事务里调用网络
```

---

# 145. 禁止事务内网络调用

错误：

```text
BEGIN DB TRANSACTION

INSERT provider

HTTP Test Connection

WAIT...

INSERT model

COMMIT
```

正确：

```text
HTTP Probe
     ↓
获得结果

BEGIN DB TRANSACTION
     ↓
持久化 Provider / Model
     ↓
COMMIT
```

数据库事务不包住外部网络。

---

# 146. 禁止事务内用户交互

同样不能：

```text
BEGIN
↓
弹 Dialog 等用户确认
↓
COMMIT
```

事务必须：

```text
短
确定
无交互。
```

---

# 147. Provider Test 保存

用户：

```text
Test Connection
```

成功后，如果要保存结果：

```text
独立短事务。
```

不应该锁住 Provider 编辑事务。

---

# 148. Optimistic Concurrency

V0.1 是单用户桌面应用。

普通业务实体不需要复杂：

```text
row_version
```

机制。

如果未来 GUI 多窗口 / CLI 同时修改同一 CAS Database，可加入：

```text
version
```

字段。

V0.1 主要通过：

```text
短事务
唯一约束
数据库锁
Application Coordination
```

保证。

---

# 149. GUI 与 CLI 并发

Desktop 和 CLI 可能同时访问：

```text
cas.db
```

因此 SQLite 配置必须允许：

```text
多进程读取
有限写竞争。
```

WAL + busy timeout 提供底层支持。

涉及：

```text
Apply
Profile Activation
Critical Mutation
```

仍需要更高层互斥机制。

---

# 150. Apply Lock 与 DB Lock 分离

```text
SQLite Write Lock
```

只能保护数据库。

```text
CAS Apply Lock
```

需要保护：

```text
数据库
+
Codex Filesystem
```

因此不能依赖 SQLite 自身锁替代：

```text
Apply Lock。
```

---

# 151. Data Directory Lock

对涉及整个 CAS 数据迁移/恢复的操作，可以增加：

```text
Application Instance Lock
```

但 V0.1 不需要强制只运行一个普通 GUI/CLI 进程。

---

# 152. 删除策略

业务主实体默认：

```text
物理删除
+
强引用校验。
```

V0.1 不默认对：

```text
Provider
Model
Agent
Profile
```

使用软删除。

---

# 153. 为什么 V0.1 不默认软删除

CAS 是本地配置管理工具。

软删除会增加：

```text
所有查询过滤
唯一键复用
关联约束
导出逻辑
```

复杂度。

真正需要历史的：

```text
Configuration Snapshot
Apply Transaction
Verification
```

单独保存即可。

---

# 154. 如果未来需要 Trash

未来可以增加：

```text
deleted_at
```

或者独立：

```text
Recycle Bin
```

但不提前污染 V0.1 核心表。

---

# 155. Provider Key 删除后复用

Provider 被真正删除后：

```text
provider_key
```

允许未来重新使用。

它不是：

```text
永久保留的全球身份。
```

内部 UUID 保证不同实体仍可区分。

---

# 156. Agent Key 删除后复用

同理：

```text
executor
```

被删除后，可以未来重新创建。

但新的 Agent：

```text
UUID 不同。
```

---

# 157. Profile Key

Profile Key 主要用于：

```text
CLI
导出
稳定引用。
```

修改 Key 应当谨慎，但数据库允许通过业务 Use Case 修改。

# 158. Cache 数据

可以：

```text

```

或者：

```text

```

临时文件。

如果需要 SQLite Cache，应单独：

```text

```

并允许随时清空。

# 182. 删除关系总览

```text

 ├─ CredentialReference → RESTRICT（应用层先协调 Secret 删除）

 ├─ Compatibility       → CASCADE
 ├─ Verification        → CASCADE
 ├─ AgentBinding        → RESTRICT
 └─ ProfileBinding      → RESTRICT

 ├─ Requirements        → CASCADE
 ├─ DirectBinding       → CASCADE
 └─ ProfileBinding      → RESTRICT

 └─ SnapshotResource    → CASCADE
```

# 183. 删除原则

CAS 的数据库约束需要确保：

> 强业务引用不得因为一次删除操作被静默级联清除。

可以级联的是：

```text
真正的从属数据。
```

例如：

```text
Model Capability
Agent Requirement
Profile 内部 Binding
```

不应该级联的是：

```text
一个独立业务实体对另一个实体的使用关系。
```

# 221. 最终设计结论

CAS 的持久化层应当保持：

```text
SQLite
=
CAS Domain State Store
```

而不是：

```text
Codex Mirror Database
```

数据库真正保存的是：

```text
用户想要怎样配置 Codex Agent Team
```

而：

```text
Codex 当前磁盘上实际是什么配置
```

仍然必须由：

```text
Codex Integration Layer
```

读取和验证。

最终关系：

```text
               SQLite
                 │
          Desired CAS State
                 │
                 ▼
       Configuration Compiler
                 │
                 ▼
         Codex Filesystem
                 │
                 ▼
          Observed State
```

通过：

```text
ManagedResource
ConfigurationState
Snapshot
ApplyTransaction
```

连接二者。

持久化设计的核心不是把更多东西保存下来，而是确保：

> 每一种数据只有一个明确的 Source of Truth。

> CAS 业务数据、Codex 外部配置、Secret、Snapshot 文件和运行时状态分别由正确的存储机制负责。

> 即使应用崩溃、Provider 暂时不可用、Codex 配置被外部修改或版本升级，CAS 的核心业务状态仍然可以被可靠读取、迁移、验证和恢复。
