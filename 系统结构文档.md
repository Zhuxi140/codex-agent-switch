# Codex Agent Switch 系统结构文档

> 文档类型：System Architecture / System Structure  
> 项目暂定名称：Codex Agent Switch  
> 简称：CAS  
> 文档职责：定义系统整体结构、模块边界、模块职责、依赖方向与运行时关系。

---

# 0. V0.1 架构基线

- 首发协议为 Responses；`deepseek-v4-flash` 是第一个经官方确认的 Direct Preset，Custom Responses Provider 是同级通用入口。
- DeepSeek 只出现在 Preset / Model Definition 数据中；Domain、Application、IPC 和 Generic Responses Adapter 禁止使用品牌分支。
- V0.1 正式平台为 Windows，只实现 Windows Credential Manager 与 Windows 安装/升级链路；跨平台接口保留但 macOS / Linux Adapter 延后。
- V0.1 只实现 Agent Base Binding；Profile Domain、Discovery、Runtime Probe、Import / Adopt 为 P1 结构。
- 正式功能开发前先通过 per-agent provider/model、command-backed credential、非破坏式 Apply/Restore、稳定 helper 路径四项 PoC Gate。

---

# 1. 文档目标

Codex Agent Switch 是一个面向 Codex Multi-Agent 能力的模型与 Agent 管理工具。

系统的核心目标不是替代 Codex，也不是自行实现一套完整 Agent Runtime，而是在 Codex 原有能力之上提供统一的管理层，使用户能够：

- 管理不同模型服务提供方；
- 管理不同模型；
- 将模型绑定到不同 Codex Agent 角色；
- 在不直接操作 Codex 配置文件的情况下切换 Agent 使用的模型；
- 保留 Codex 官方模型和原有配置；
- 为未来不同模型协议和不同 Provider 留出扩展能力。

系统设计必须遵循以下核心关系：

```text
Agent Role
    ↓
Model
    ↓
Provider
    ↓
Protocol / Runtime
```

其中：

```text
Agent ≠ Model
Model ≠ Provider
Provider ≠ Protocol
```

任何一层不得与下一层形成硬编码绑定。

# 2. 系统定位

CAS 位于用户与 Codex 配置系统之间。

整体关系：

```text
┌──────────────────────────────────────┐
│                User                  │
└──────────────────┬───────────────────┘
                   │
                   ▼
┌──────────────────────────────────────┐
│        Codex Agent Switch            │
│                                      │
│  Provider Management                 │
│  Model Management                    │
│  Agent Management                    │
│  Profile Management                  │
│  Configuration Management            │
│  Secret Management                   │
└──────────────────┬───────────────────┘
                   │
                   │ Generate / Patch
                   ▼
┌──────────────────────────────────────┐
│          Codex Configuration         │
│                                      │
│  config.toml                         │
│  agents/*.toml                       │
│  model catalogs                      │
└──────────────────┬───────────────────┘
                   │
                   ▼
┌──────────────────────────────────────┐
│              Codex Runtime           │
│                                      │
│ Primary Agent                        │
│ Subagents                            │
│ Tool Runtime                         │
│ Sandbox                              │
└──────────────────┬───────────────────┘
                   │
                   ▼
┌──────────────────────────────────────┐
│          Model Providers             │
│                                      │
│ OpenAI                               │
│ DeepSeek                             │
│ OpenRouter                           │
│ Custom Provider                      │
│ Future Providers                     │
└──────────────────────────────────────┘
```

CAS 不参与 Codex 主 Agent 与 Subagent 的实际推理过程。

CAS 的职责结束于：

> 为 Codex 生成正确、稳定、可恢复的运行配置。

实际 Agent 生命周期、上下文管理、工具调用、代码执行、模型请求等仍由 Codex Runtime 负责。

# 3. 核心架构原则

## 3.1 管理层与运行时分离

CAS 是配置管理系统，而不是 Agent Runtime。

```text
CAS
负责：
配置
管理
映射
生成
切换
诊断

Codex
负责：
推理
Agent Spawn
上下文
工具调用
代码修改
任务执行
```

禁止 CAS 直接侵入 Codex Agent Runtime。

---

## 3.2 Agent Role 与模型解耦

Agent 角色描述的是职责，而不是模型。

例如：

```text
executor
explorer
reviewer
tester
```

不得设计为：

```text
deepseek_worker
gpt_reviewer
gemini_explorer
```

正确关系：

```text
executor
    ↓
deepseek-v4-flash
```

后续可以直接调整为：

```text
executor
    ↓
other-model
```

而：

```text
executor
```

自身职责保持不变。

---

## 3.3 Model 与 Provider 解耦

Model 表示模型本身。

Provider 表示模型请求的服务来源。

例如：

```text
Model
qwen-coder

Provider A
官方 API

Provider B
OpenRouter

Provider C
企业代理
```

相同或兼容的模型可能通过不同 Provider 提供。

因此禁止将：

```text
model_id
```

直接作为 Provider 身份。

---

## 3.4 Provider 与协议解耦

Provider 描述服务提供方。

Protocol 描述 CAS/Codex 与该服务通信的方式。

例如：

```text
DeepSeek
    ↓
Responses API
```

未来可能存在：

```text
Provider A
    ↓
OpenAI Responses

Provider B
    ↓
OpenAI Chat Completions

Provider C
    ↓
Anthropic Messages

Provider D
    ↓
CAS Gateway
    ↓
Responses
```

协议能力必须作为独立系统边界存在。

---

## 3.5 CAS 内部状态与 Codex 配置分离

CAS 自己维护系统状态。

Codex 配置文件只是 CAS 根据当前状态产生的：

```text
Projection
```

即：

```text
CAS Internal State
        ↓
Configuration Compiler
        ↓
Codex Configuration
```

不得把：

```text
~/.codex/config.toml
```

直接作为 CAS 的业务数据库。

---

## 3.6 非破坏式配置修改

CAS 不拥有整个 Codex 配置文件。

CAS 只允许管理自己明确声明拥有的配置区域。

例如：

```text
CAS-owned

model_providers.cas_xxx
agents.executor
agents.reviewer
CAS 创建的 agent TOML
CAS 创建的 model catalog
```

而：

```text
用户 MCP 配置
用户 project 配置
用户其他 model provider
Codex 自身设置
未知的新版本字段
```

都属于：

```text
External-owned
```

不得覆盖。

# 4. 系统分层结构

CAS 建议划分为六个主要层级：

```text
┌───────────────────────────────────────┐
│         Presentation Layer            │
├───────────────────────────────────────┤
│         Application Layer             │
├───────────────────────────────────────┤
│           Domain Layer                │
├───────────────────────────────────────┤
│      Configuration Integration        │
├───────────────────────────────────────┤
│      Infrastructure Layer             │
├───────────────────────────────────────┤
│     External Runtime / Providers      │
└───────────────────────────────────────┘
```

依赖方向必须保持：

```text
Presentation
      ↓
Application
      ↓
Domain

Infrastructure
      ↑
Application

Codex Integration
      ↑
Application
```

Domain 不允许反向依赖 GUI、Codex 文件结构或具体数据库实现。

---

# 5. Presentation Layer

Presentation Layer 负责与用户交互。

它只负责：

- 接收用户操作；
- 展示系统当前状态；
- 调用 Application Layer；
- 展示操作结果；
- 展示错误与诊断信息。

Presentation Layer 不负责：

- 修改 Codex 配置；
- 保存 Provider；
- 操作密钥；
- 解析 TOML；
- 判断模型兼容性；
- 编排 Agent；
- 生成 Agent 配置。

系统允许存在多个 Presentation Adapter：

```text
Presentation
├── Desktop GUI
└── CLI
```

二者必须共享相同 Application Layer。

禁止出现：

```text
GUI 自己实现一套 Provider 管理
CLI 再实现另一套 Provider 管理
```

---

# 6. Application Layer

Application Layer 是系统用例编排层。

负责协调 Domain、Repository、Codex Integration 和系统基础设施。

主要模块：

```text
Application
├── Provider Application Service
├── Model Application Service
├── Agent Application Service
├── Profile Application Service
├── Configuration Application Service
├── Secret Application Service
└── Diagnostic Application Service
```

Application Layer 不应该包含底层：

```text
TOML AST 操作
SQLite SQL
HTTP Client 实现
Windows Credential API
文件复制实现
```

这些属于 Infrastructure。

---

# 7. Domain Layer

Domain Layer 描述 CAS 自身最核心的业务概念。

建议至少包含以下领域：

```text
Domain
├── Provider
├── Model
├── Agent
├── Profile
├── Protocol
├── Capability
└── Configuration Ownership
```

Domain Layer 不感知：

```text
React
Tauri
SQLite
toml_edit
Codex 配置具体文件路径
Windows
macOS
Linux
```

---

# 8. Provider Domain

Provider 表示一个模型服务来源。

例如：

```text
DeepSeek
OpenAI Compatible Provider
OpenRouter
Local Gateway
Custom Provider
```

Provider 负责描述：

```text
Provider Identity
Provider Endpoint
Authentication Strategy
Protocol
Provider Capability
Provider Status
```

Provider 不负责：

```text
Agent Role
Agent Instructions
模型选择策略
Codex agent.toml 生成
```

关系：

```text
Provider
    │
    ├── Model A
    ├── Model B
    └── Model C
```

一个 Provider 可以存在多个 Model。

---

# 9. Model Domain

Model 描述 CAS 可以使用的模型。

Model 负责表达：

```text
模型身份
Provider 所属关系
模型能力
上下文能力
Reasoning 能力
Tool 能力
Codex Compatibility
```

Model 不承担 Agent 职责。

错误设计：

```text
DeepSeekExecutorModel
ReviewerGPTModel
```

正确设计：

```text
Model
└── deepseek-v4-flash

Agent
└── executor

Binding
executor → deepseek-v4-flash
```

---

# 10. Agent Domain

Agent 是 CAS 中非常重要的一层。

Agent 表示：

> Codex 中一个具有明确职责的 Subagent Role。

例如：

```text
executor
explorer
reviewer
tester
database_expert
frontend_worker
custom_agent
```

Agent 包含的是：

```text
职责
描述
Instructions
运行权限
Sandbox 策略
Reasoning 偏好
模型绑定
```

Agent 不应该直接保存：

```text
API Key
Provider Endpoint
HTTP 配置
```

Agent 通过 Model Binding 间接连接 Provider。

关系：

```text
Agent
    ↓
Agent Model Binding
    ↓
Model
    ↓
Provider
```

---

# 11. Profile Domain（P1）

本节保留长期领域边界；V0.1 不实例化 Profile Domain / Service / Repository。

Profile 表示一组完整 Agent 配置组合。

结构概念：

```text
Profile
│
├── executor → Model A
├── explorer → Model B
├── reviewer → Model C
└── tester   → Model D
```

Profile 的职责仅限于：

> 描述一组 Agent Binding。

Profile 不承担：

```text
Provider 配置管理
密钥管理
Agent Instruction 定义
Codex 文件写入
```

Profile 被激活后，由 Application Layer 请求 Configuration System 进行配置同步。

---

# 12. Protocol Domain

Protocol 层用于描述模型访问协议能力。

第一阶段核心能力：

```text
Responses API
```

未来允许扩展：

```text
Responses API
Chat Completions
Anthropic Messages
Custom Adapter
Local Gateway
```

Protocol 不直接与 GUI 或 Agent 发生关系。

正确结构：

```text
Agent
 ↓
Model
 ↓
Provider
 ↓
Protocol
```

---

# 13. Capability System

不同模型和 Provider 的能力不完全相同。

因此需要统一 Capability 抽象。

例如：

```text
ToolCalling
ParallelToolCalling
Reasoning
StructuredOutput
LargeContext
CodexMultiAgent
ResponsesAPI
Streaming
```

Capability System 用于：

```text
兼容性判断
Agent 模型选择约束
配置合法性判断
诊断
```

禁止在业务代码中大量出现：

```text
if provider == "deepseek"
if model == "xxx"
```

应优先使用：

```text
model.capabilities.supports(...)
```

这样新增模型时无需修改核心业务逻辑。

---

# 14. Codex Integration Layer

Codex Integration 是 CAS 与 Codex 的边界层。

负责：

```text
检测 Codex 环境
定位 CODEX_HOME
读取 Codex 配置
分析当前配置
生成 CAS 管理配置
Patch Codex 配置
创建 Agent 配置
创建 Model Catalog
检查 Codex 兼容性
```

建议拆分：

```text
Codex Integration
├── Codex Environment Detector
├── Codex Config Reader
├── Codex Config Parser
├── Codex Config Patcher
├── Agent Config Generator
├── Model Catalog Manager
├── Ownership Manager
└── Codex Compatibility Checker
```

---

# 15. Codex Environment Detector

负责检测：

```text
Codex 是否安装
Codex 可执行文件位置
Codex 版本
CODEX_HOME
默认配置目录
当前平台
```

它只负责环境发现。

不得负责：

```text
修改 config.toml
生成 Agent
创建 Provider
```

---

# 16. Codex Config Reader

负责读取：

```text
config.toml
agents/*.toml
CAS 管理的 catalog
```

输出统一内部表示。

Reader 必须是：

```text
Read Only
```

不得执行任何写操作。

---

# 17. Codex Config Patcher

Config Patcher 专门负责：

> 对现有 Codex 配置进行非破坏式修改。

处理过程：

```text
Existing config.toml
        ↓
Parse
        ↓
Ownership Analysis
        ↓
Generate Patch
        ↓
Apply Patch
        ↓
Validate
        ↓
Atomic Replace
```

不得采用：

```text
读取部分字段
↓
重新 serialize 整个 config.toml
```

的方式更新用户配置。

---

# 18. Agent Config Generator

Agent Config Generator 将 CAS Agent Domain 转换为 Codex Agent 配置。

关系：

```text
CAS Agent
   +
Model Binding
   +
Provider Binding
        ↓
Agent Config Generator
        ↓
Codex Agent TOML
```

Generator 只负责：

```text
Domain → Codex Representation
```

不负责保存 Domain 数据。

---

# 19. Model Catalog Manager

Model Catalog Manager 用于处理 Codex 所需的模型能力描述。

主要负责：

```text
Model Metadata
Codex Model Catalog
Catalog Validation
Catalog Generation
Catalog Version
```

它与 Provider 配置分离。

原因：

```text
Provider
描述连接方式

Model Catalog
描述模型能力
```

两者不能混为同一个模块。

---

# 20. Configuration Ownership Manager

这是 CAS 的关键安全边界模块。

用于明确：

```text
哪些配置属于 CAS
哪些配置属于用户
哪些配置属于其他工具
```

CAS-owned 内容建议统一使用明确命名空间。

例如：

```text
cas_deepseek
cas_openrouter
cas_custom_xxx
```

Agent 文件也记录 CAS Ownership Metadata。

逻辑上：

```text
Codex Configuration
│
├── User-owned
├── Codex-owned
├── Third-party-owned
└── CAS-owned
```

CAS 只能无条件修改：

```text
CAS-owned
```

对于其他区域只能：

```text
Read
Preserve
```

---

# 21. Configuration Compiler

系统需要一个独立 Configuration Compiler。

其作用类似：

```text
CAS Internal State
        ↓
Resolve
        ↓
Validate
        ↓
Compile
        ↓
Codex Configuration Projection
```

Compiler 的输入：

```text
Active Profile
Agents
Models
Providers
Capabilities
Codex Environment
```

输出：

```text
Configuration Plan
```

例如：

```text
Add provider cas_deepseek
Update executor.toml
Create model catalog
Remove obsolete CAS provider
Preserve external config
```

Compiler 本身：

```text
不执行文件写入
```

实际写入由：

```text
Configuration Writer
```

负责。

这种设计可以把：

```text
“应该改什么”
```

和：

```text
“实际怎么改文件”
```

分离。

---

# 22. Configuration Writer

Configuration Writer 执行 Configuration Plan。

负责：

```text
文件创建
文件 Patch
目录创建
原子写入
文件替换
写入失败恢复
```

不负责：

```text
业务规则判断
Agent Binding
Provider Compatibility
```

---

# 23. Backup & Recovery 模块

任何修改 Codex 配置之前，都必须经过 Backup & Recovery 边界。

结构：

```text
Configuration Application Service
        ↓
Backup Manager
        ↓
Configuration Writer
```

Backup Manager 负责：

```text
创建配置快照
记录修改前状态
恢复历史配置
异常恢复
```

Backup 不属于 Profile。

Profile 是：

```text
CAS 的逻辑配置组合
```

Backup 是：

```text
Codex 实际文件状态快照
```

二者不得混淆。

---

# 24. Secret Management

Secret Management 独立于 Provider Management。

Provider 只保存：

```text
Secret Reference
```

而不是：

```text
API Key 明文
```

结构：

```text
Provider
   │
   └── credentialRef
            │
            ▼
      Secret Manager
            │
    ┌───────┼────────┐
    ▼       ▼        ▼
 Windows  macOS    Linux
Credential Keychain Secret
 Manager           Service
```

Secret Manager 提供统一抽象：

```text
save
read
delete
exists
```

Provider 不感知底层系统。

---

# 25. Credential Helper

为了支持 Codex 动态获取凭据，可以提供独立 Helper：

```text
cas-helper
```

其职责非常单一：

```text
Codex
   ↓
cas-helper token <credential>
   ↓
Secret Manager
   ↓
stdout token
```

Helper 不负责：

```text
GUI
Provider 编辑
Profile
Agent
配置生成
```

这样 Helper 可以保持极小体积和极少攻击面。

---

# 26. Persistence Layer

CAS 自己的业务状态通过 Repository 层访问。

结构：

```text
Application
    ↓
Repository Interface
    ↓
Infrastructure Repository
    ↓
Local Persistence
```

Repository 至少按领域进行职责拆分：

```text
ProviderRepository
ModelRepository
AgentRepository
ProfileRepository
ApplicationSettingRepository
```

Domain 和 Application 不直接依赖：

```text
SQLite
具体 SQL
文件格式
```

---

# 27. Provider Adapter

不同 Provider 的特殊能力通过 Adapter 隔离。

结构：

```text
ProviderService
      ↓
ProviderAdapter
      │
      ├── NativeResponsesAdapter
      ├── CustomResponsesAdapter
      └── FutureGatewayAdapter
```

Provider Adapter 主要用于：

```text
连接测试
能力检测
模型发现
协议校验
Provider 特殊兼容逻辑
```

禁止 Provider 特殊逻辑进入：

```text
AgentService
ProfileService
GUI
Config Writer
```

---

# 28. Gateway Boundary

Gateway 不属于 V0.1 核心运行链路，但系统结构必须预留边界。

未来：

```text
Codex
  │
Responses
  │
  ▼
CAS Local Gateway
  │
  ├── Chat Completions Provider
  ├── Anthropic Provider
  ├── Gemini Provider
  └── Other Protocol
```

Gateway 必须作为：

```text
独立模块
```

存在。

不得让协议转换代码散落在：

```text
Provider Manager
Agent Manager
Config Generator
```

中。

逻辑结构：

```text
Gateway
├── Request Normalizer
├── Protocol Translator
├── Tool Call Translator
├── Stream Translator
└── Provider Transport
```

CAS Core 只知道：

```text
这个 Provider 通过 Gateway 可提供 Codex-Compatible Responses
```

而不关心转换实现。

---

# 29. Diagnostic System

Diagnostic System 负责检测当前 CAS 与 Codex 的结构是否一致。

结构：

```text
Diagnostic Service
│
├── Environment Check
├── Configuration Check
├── Provider Check
├── Model Check
├── Agent Check
├── Credential Check
└── Compatibility Check
```

Diagnostic 只做：

```text
检测
分析
报告
```

不得隐式修改配置。

如果未来需要：

```text
Repair
```

应由用户显式触发独立 Repair Use Case。

---

# 30. Event / Change Notification

为了降低模块间直接依赖，可以保留内部事件机制。

例如：

```text
ProviderUpdated
ModelUpdated
AgentUpdated
ProfileActivated
ConfigurationApplied
CredentialChanged
```

使用场景：

```text
Profile Activated
       ↓
Configuration needs recompilation
```

而不是：

```text
ProfileService
直接操作
ConfigWriter
```

第一版不要求实现复杂 Event Bus。

可以保持：

```text
Application Event
```

级别的轻量抽象。

完整结构：

```text
Codex Agent Switch
│
├── Presentation
│   ├── Desktop GUI
│   └── CLI
│
├── Application
```

# 33. 模型切换结构

模型切换不修改 Agent Role。

例如：

```text
Before

executor
   ↓
DeepSeek V4 Flash
   ↓
DeepSeek
```

切换后：

```text
executor
   ↓
Model X
   ↓
Provider X
```

Application Layer 执行：

```text
Change Agent Binding
        ↓
Validate Compatibility
        ↓
Compile Configuration
        ↓
Generate Patch
        ↓
Apply
```

不得：

```text
删除 executor
重新创建另一个 provider-specific agent
```

# 34. Profile 切换结构

Profile 切换只修改：

```text
Agent → Model Binding Set
```

例如：

```text
Balanced
│
├─ executor → Model A
├─ explorer → Model B
└─ reviewer → Model C
```

切换：

```text
Quality
│
├─ executor → Model D
├─ explorer → Model E
└─ reviewer → Model F
```

核心 Agent Role 本身仍然不变。

# 48. Codex 依赖边界

CAS 必须假设：

> Codex 会继续变化。

因此禁止把当前 Codex 的 TOML 结构传播到整个项目。

正确方式：

```text
Domain Agent
        ↓
CodexAgentConfigMapper
        ↓
Codex-specific TOML
```

而不是：

```text
Agent Domain
直接拥有
model_provider
sandbox_mode
config_file
```

如果某字段纯粹属于 Codex 实现细节，应存在：

```text
cas-codex
```

而不是核心 Domain。

---

# 49. Provider 依赖边界

同样必须假设：

> Provider 会不断增加。

核心系统不能知道：

```text
DeepSeek 有什么特殊字段
Kimi 有什么特殊字段
某厂商 URL 怎么拼
```

这些必须进入：

```text
ProviderPreset
```

或者：

```text
ProviderAdapter
```

---

# 50. 扩展模型

系统扩展新的 Provider：

```text
Add Provider Preset
        +
必要时 Add Adapter
```

不应修改：

```text
Agent Core
Profile Core
Codex Core
GUI 核心业务
```

新增 Agent Role：

```text
Add Agent Definition
```

不应修改：

```text
Provider
Model
Protocol
```

新增 Protocol：

```text
Add Protocol Adapter
```

不应修改：

```text
Agent Role
Profile
```

这就是系统保持长期可维护性的关键。

# 53. 系统核心不变量

整个项目开发过程中必须长期保持以下不变量。

### 不变量一

```text
Agent Role 不依赖具体 Model。
```

### 不变量二

```text
Model 不依赖具体 Agent Role。
```

### 不变量三

```text
Provider 不参与 Agent 业务逻辑。
```

### 不变量四

```text
CAS Internal State 是管理状态来源，
Codex Config 是生成结果。
```

### 不变量五

```text
CAS 不拥有完整 Codex 配置。
```

### 不变量六

```text
任何配置修改必须可恢复。
```

### 不变量七

```text
GUI 与 CLI 使用相同 Application Layer。
```

### 不变量八

```text
平台差异必须被 Infrastructure 隔离。
```

### 不变量九

```text
Provider 特殊行为不得进入 Domain Core。
```

### 不变量十

```text
CAS 不重新实现 Codex Agent Runtime。
```

# 55. 架构结论

Codex Agent Switch 不应围绕某一个模型构建。

系统真正管理的是：

```text
Agent Role
     ↓
Model Binding
     ↓
Provider
```

Codex 负责：

```text
Agent Runtime
```

CAS 负责：

```text
Agent Configuration Management
```

通过：

```text
Domain 与 Codex 解耦
Agent 与 Model 解耦
Model 与 Provider 解耦
Provider 与 Protocol 解耦
内部状态与 Codex 文件解耦
```

使系统最终能够从：

```text
GPT Primary
    +
DeepSeek Executor
```

自然扩展为：

```text
Primary
Executor
Explorer
Reviewer
Tester
Custom Agent
        ↓
任意兼容 Model
        ↓
任意兼容 Provider
```

而不需要重构核心架构。
